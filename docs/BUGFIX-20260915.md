## 一、致命 BUG：3 个人显示「已加入世界 9 人」+ 第二个人连不上

### 根因（两个现象是同一个病）

中继在 `try_pair()` 里**一配上对**就把会话写进 `room.sessions`：

```python
self.sessions[session_id] = pair      # 配对成功 = 立刻占一个名额
```

但"配上对"**不等于**"进了世界"。配对之后还要走：

```
PLAYER 与 HOST_TUNNEL 配对
   → 房主客户端连本机 Minecraft → 回 READY
   → 玩家侧收到 READY → 回 CONNECTED → 才开始转发字节
```

而这段握手**两处都没有超时**：

* `handle_host_tunnel()`：`line = await reader.readline()`（等 READY，无超时）
* `handle_player()`：`await pair.host_ready.wait()`（等 READY，无超时）

于是任何一次"配上但对不上"（房主本机 MC 拒连、隧道半开、客户端重连）都会
**永久留下一个幽灵会话**。而显示口径正是：

```python
players = (1 if 房主 else 0) + len(self.sessions)
```

所以：

1. **人数虚高** —— 房主 1 + 8 个幽灵 = 「已加入世界 9 人」；
2. **更致命** —— `try_pair()` 的容量判断是 `len(self.sessions) >= capacity`，
   幽灵会话把名额吃光，**第二个人再也配不上对 → 游戏直接连不上**。

客户端侧的隧道重连很积极（一次失败会重开隧道、玩家侧也会重试），
所以每次重试都添一个幽灵，数字一路涨到 8、9 完全说得通。

### 修法（`server/relay_server.py` + `server/room_members.py` + `server/relay_config.py`）

| # | 改动 | 作用 |
|---|------|------|
| 1 | `Pair.established` 标记，只有真的走到 `CONNECTED` 才置 True | 区分"占位会话"与"真进世界" |
| 2 | 新增 `Room.world_players()`：只数 `established`，并按玩家名去重 | 显示口径回到真实人数（同名重连不重复计） |
| 3 | `Room.snapshot()["players"]` 改用它 | 面板/客户端同一个口径 |
| 4 | `room_members.world_player_count()` 复用同一个实现 | 客户端「已加入世界」（HOST_STATE `world=`）同口径 |
| 5 | 新增 `_pair_handshake_deadline()` 看门狗：`PAIR_HANDSHAKE_TIMEOUT`（默认 20s）到点还没成 → 拆掉整对、**名额归还** | 这才是"第二个人能进来"的解药 |
| 6 | `handle_host_tunnel` 等 READY 加超时：`PAIR_READY_TIMEOUT`（默认 15s） | 卡死的隧道不会永久挂着 |
| 7 | `remove_session()` 里 `host_ready.set()` / `start_relay.set()` + 取消看门狗 | 对面 handler 不再永久 `await`（任务泄漏） |
| 8 | 玩家进/出世界时补 `broadcast_member_state()` | 客户端那个数字**实时**更新，不再停在旧值 |

### 回归测试（`tests/session_lifecycle_test.py`，16 项全绿）

真起中继子进程 + 真协议行，关键断言：

* 配上对但没走完握手时，`players` 仍然 = 1（**修复前会是 2，并一路涨到 9**）
* 握手超时后幽灵会话被回收，且玩家 socket 被服务端关闭（不是挂着）
* 名额确实还回来了：新玩家能配对、能走完握手、收到 `CONNECTED`
* 真的进世界后 `players` = 2；同名重复连接按人去重仍为 2

## 二、服务端日志（用户：「服务端日志在哪里啊？找不到一点」）

### 当时的真相

中继的 `log()` 就是一句 `print()`：日志只落在**容器标准输出**里。
想看只能 `docker logs mc-relay`，翻不了历史、没法按时间找、更没法发给别人排查；
容器一重建就没了。

### 现在（新增 `server/relay_log.py`）

* **写文件 + 大小轮转**：`/app/logs/relay.log`，5MB 轮转，保留 3 份历史
  （compose 里挂 `./logs:/app/logs`，**重建容器日志不丢**）；
* **内存环形缓冲**：最近 4000 行，面板"最近 N 行"直接取，不怕文件刚好在轮转；
* 写日志的任何失败都被吞掉 —— **日志是旁路，绝不影响 Minecraft 连接**。

### 面板可导出下载

| 接口 | 作用 |
|------|------|
| `GET /logs/tail?lines=N` | JSON，面板预览 / 显示"当前多少行、多大" |
| `GET /logs/export` | `text/plain` + `Content-Disposition: attachment`，浏览器**直接下载** |

面板「操作日志」页新增 **「下载服务端日志」** 按钮（POST + CSRF，仅管理员可见）；
中继若还是旧版，按钮会明确提示「中继暂不支持日志导出（需要更新服务端）」。

* 测试：`tests/server_logs_test.py` 12 项全绿（真起中继，真去请求两个接口）。
* **Dockerfile 必须 COPY `relay_log.py`**（已补），否则容器直接起不来。

## 三、全客户端潜伏 BUG 扫描（只读审计）

用「本 BUG 的模式」——**显示的数字/状态来自两个来源，或在事情发生前就计数**——
把客户端整个扫了一遍，找到 7 个真问题（另有 6 条低优先备注）。已交由修复代理处理：

| 级别 | 位置 | 问题 |
|------|------|------|
| 高 | `core/room.py` | 读循环无超时、ping 从不核对 PONG → 网络黑洞时界面永远显示陈旧人数（本 BUG 的客户端镜像） |
| 高 | `core/session.py` | 中继拒 token / 账号被禁用后状态永远停在「运行中」，头部还写「已连接中转服务器」 |
| 高 | `core/room.py` | 迟到 6 秒的 `room_gone` 能拆掉用户**之后新建的房间** |
| 中 | `gui/app.py` | 「已加入世界」算好之后被无条件覆盖，且主机侧取本地计数、玩家侧取中继计数 —— 同一个房间两侧数字不一致 |
| 中 | `core/engine.py` | 启动超时后留下**无法停止**的幽灵会话（仍占着中继房间/隧道） |
| 中 | `core/host_core.py` | DELETE 回复超时后，之后控制通道上任何 ERROR 都被当作删除结果（串台） |
| 中 | `core/player_core.py` | 玩家侧「本地连接 N」在配对成功前就上报（同"提前计数"模式） |
