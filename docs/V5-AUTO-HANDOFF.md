# MCLink v5.0.0 AUTO 开发交接方案

## 2026-10-19 用户补充的硬性边界（优先于下文应用措辞）

本项目提供通用网络层端口联机服务，Minecraft 只是应用之一。用户点开始连接后，NAT、入站、打洞、中继／直连隧道及 AUTO 迁移必须独立建立和验证，不能依赖游戏进程已启动、目标端口已监听或本地应用已接入代理。应用稍后接入只附着到既有网络服务。应用未启动不构成网络隧道建立失败。

手动网络核心以 v3.9.20Full 为固定基准；AUTO 通过独立适配和调度扩展。修复记录与补充协议见 docs/V5-NETWORK-R1.md、docs/AUTO-PROTOCOL.md，固定核心指纹见 docs/manual-core-baseline.json。


> 用户于 2026-10-19 确认并授权执行。本文件保存已确认方案；实际实现和验证见开发副本内的执行记录。

## 1. 基线与已确认目标

**开发基线：`v3.9.20Full`。首个完整交付版本：`v5.0.0`。**

`dsh` 仅供查阅历史资料，不继承其开发进度。现有手动中继、手动直连的业务行为保持一致。

原计划模式中尚未落盘的交接文档，现保存于工作区 `V5-AUTO-HANDOFF.md`。从基线复制出 `v5.0.0Full` 开发目录，保留原交付目录供对照。

### 已与用户确认

- AUTO 是**房间级策略**，由 Owner 设置；Owner 与 Host 可以是不同成员。
- 保留“开始连接”操作。选择 AUTO、建房或入房本身不替玩家启动游戏通道。
- 开始连接后，**先建立中继承载，游戏数据无需等待打洞**；后台同时尝试直连。
- 新加入 AUTO 房间的玩家遵循同样流程。
- 直连验证成功后，已有游戏连接切到直连，中继保持可用备用。
- 直连故障后自动回到中继，尽量保持 Minecraft 连接不断；故障检测可能造成短暂卡顿。
- 每个 Host–Player 配对独立管理，允许同房同时存在直连玩家和中继玩家。
- **仅要求 AUTO 内部切换保持游戏连接。** 手动模式与 AUTO 之间切换允许重连一次。
- Host 在“打洞进度”下逐人显示实际连接状态及 IP 信息；Panel 同步展示路径、备用状态、切换原因。
- 不支持 AUTO 协议的旧客户端不能进入 AUTO 房间。

## 2. 核心实现：让游戏连接独立于传输路径

### 持续存在的游戏流

新增 AUTO 专用传输层，置于本地 Minecraft TCP 连接与中继／直连承载之间。

每条 Minecraft TCP 连接对应一个 `AutoStream`，持续持有：

- 原来的本地 TCP reader/writer；
- 唯一逻辑会话 ID；
- 两个方向各自的字节序号、确认进度；
- 有界发送重放缓存、接收重排缓存；
- 正常结束、异常终止状态。

**切换路径不得重新连接 Host 的 Minecraft 后端，也不得关闭 Player 的本地 Minecraft socket。**

中继从第一个游戏字节开始传输 AUTO 帧。直连建立后承载同一种帧，两路始终可以接收，最终汇入同一个逻辑流。

### 数据正确性要求

- 每个方向使用独立的 64 位字节偏移量；根据会话 ID 和偏移量去重、重排，按序向 Minecraft 写入一次。
- 发送端保留所有未获得端到端确认的数据；故障后通过可用路径重放。
- 接收端只有可靠接纳数据后才能确认；缓存满时使用背压，暂停继续读取。
- **禁止丢弃已经从本地 TCP 读出的字节。原 TCP 不会替代理内部的数据丢失补传。**
- 两条路径分别保留帧解析状态；不能因超时取消半帧读取后，把剩余内容当成新帧。
- 正常 EOF 携带最终偏移量，待此前数据交付完毕再结束对应方向；异常终止使用明确的 RESET。
- 路径失效只关闭该路径，不能直接销毁 `AutoStream`。

### 身份与多人隔离

服务端为 AUTO 配对分配唯一会话 ID，绑定房间实例、当前 Host 开服代次、Host 身份和 Player 身份，并向两端提供一致的配对信息。

- 必须精确选择对应 Player 的直连链路。
- 禁止使用“第一个可用直连”或 FIFO 备用后端认领来匹配 AUTO 游戏流。
- 一个玩家可以同时有多条 Minecraft TCP 流，例如服务器列表探测和实际登录；逐流传输，逐玩家汇总展示。
- 每条新游戏流均先建立中继承载。已有健康直连可加快随后升级，但不能跳过该流的中继准备。
- Host 更换或重新开服后，旧会话、旧恢复凭证和旧控制消息失效。

### 协议接口

新增明确的 `auto_stream_v1` 能力协商。AUTO 握手返回会话 ID、两端身份、Host 代次及受身份校验保护的恢复凭证；手动模式保留原有传输分支。

AUTO 帧至少支持：

`DATA`、`ACK/WINDOW`、`PING/PONG`、`PREPARE/READY/COMMIT`、`FALLBACK`、`FIN`、`RESET`。

数据帧包含版本、类型、会话 ID、偏移量与长度。路径控制消息另带递增切换代号，迟到的升级指令不能恢复已取消的切换。

服务端继续转发不透明的数据帧；端到端确认由两个客户端完成。

### 复用边界

复用现有房间管理、打洞协调、NAT 探测及已经验证的 UDP 建链能力。

AUTO 使用独立适配层：

- 不直接启用未接线的旧 `ReliableStream.migrate()`。
- 不使用现有 `DirectCarrier` 的后端认领和“关直连即关游戏流”流程。
- UDP 承载增加 AUTO 专用严格行为：队列满不能丢数据后确认；发送失败必须明确报告；部分帧发送失败后废弃该路径并重建。
- 同一共享直连承载只有一个完整帧串行发送器，防止多个游戏流交错写坏帧。

## 3. 自动选路、恢复与生命周期

### 状态流程

`中继连接中 → 中继承载／后台打洞 → 直连验证 → 切换中 → 直连承载／中继备用`

直连失败进入：

`中继承载／等待重试`

具体规则：

- 中继就绪后立即允许游戏数据通过。
- 打洞成功仅表示候选路径存在；完成双向数据探测后，才允许迁移游戏业务。
- 正常升级由 Host 协调 `PREPARE → READY → COMMIT`。
- 故障回退允许任意一端立即执行：经中继重放未确认数据，同时通知对端。不能等待故障直连排空。
- 两端始终接受合法的两路数据，避免短暂切换不同步造成断流。
- 单个玩家的重试、升级或回退不重启房间，也不影响其他玩家。
- AUTO 的实际路径变化不能触发房间 `CONNMODE`、全房断链或 GUI 的 stop/start 重建流程。

### 首版默认参数

以下为执行默认值，集中配置；后续根据测试证据调整并记录：

| 项目 | 默认行为 |
|---|---|
| 直连优先级 | 双向验证健康后优先直连，不要求延迟优于中继 |
| 升级验证 | 至少 1 秒稳定观察、3 次成功探测及双向有效负载验证 |
| 直连健康探测 | 每 1 秒一次；同时观察有待确认数据时的 ACK 进展 |
| 黑洞判定 | 超时取 `max(2 秒, 4 × 实测 RTT)`，上限 5 秒 |
| 背压处理 | 对端窗口关闭不单独视为直连故障 |
| 直连失败重试 | 5、15、30、60 秒退避，之后保持 60 秒，加入少量随机抖动 |
| 反复切换 | 60 秒内回退 3 次，暂停升级 120 秒 |
| 中继备用检测 | 每 2 秒探测；连续 6 秒无响应标记不可用并重接 |
| 中继重接 | 1、2、4、8、10 秒退避，之后保持 10 秒 |
| 双路均不可用 | 最多保留逻辑流 15 秒并背压；超时明确结束，Minecraft 可能先自行超时 |
| 数据缓存 | 每流每方向发送、接收各上限 4 MiB；AUTO 数据缓存进程总预算 128 MiB |

### 中继备用恢复

中继备用连接断开而直连仍健康时：

- 游戏继续走直连，显示“中继备用恢复中”。
- 使用原逻辑会话 ID 和恢复凭证重新附着中继。
- 服务端校验成员、Host 代次和会话归属；不能新建 Minecraft 后端连接。
- 新中继附着完成后交换确认进度，恢复备用状态。
- 旧中继连接的迟到清理不能删除已经恢复的新连接。

尚未有中继承载的新游戏连接，仍等待中继恢复后才能开始。

### 管理规则

本版沿用现有房间控制连接、身份保留和超时清理语义；不新增脱离房间控制服务继续长期游戏的模式。

明确停止、退出、被踢、关房、Host 释放或更换均属于终止事件，优先于自动恢复。服务端整体重启、游戏进程退出及两条路径长期不可用，不属于保持连接的保证范围。

旧客户端加入 AUTO 房间时明确拒绝；房间已有不兼容成员时，拒绝切到 AUTO 并列出相关成员。能力校验独立于已有版本检查旁路开关。

## 4. 客户端与 Panel 展示

### 逐玩家状态

Host 的“打洞进度”下按玩家稳定展示，不以“是否正在打洞”决定是否出行。覆盖手动中继、手动直连和 AUTO。

示例：

```text
玩家 A｜P2P 直连｜公网 IP：…｜直连端点：…:…｜24 ms｜中继备用就绪
玩家 B｜中继｜公网 IP：…｜中继 RTT：…｜正在尝试直连
玩家 C｜中继｜公网 IP：…｜中继 RTT：…｜直连暂不可用，稍后重试
```

展示规则：

- 玩家公网 IP 使用服务端实际观察到的地址，并注明来源；不能用中继服务器地址代替。
- 直连端点使用当前真实选中的地址和端口，可能是公网、局域网或 IPv6 地址；IPv6 端点使用方括号。
- 候选地址只能标为“候选”，不能冒充实际承载端点。
- 中继 RTT 使用 Host–Player 经中继的实测往返时间，不能拿单端到服务器延迟冒充。
- 未取得的信息显示“未知”或 `—`，不推测、不伪造。
- 尚未开始连接的成员显示“未开始”；中继玩家、打洞失败玩家持续显示。
- 同一玩家多流处于不同路径时显示“切换中／部分直连”。
- Player 客户端显示自己到当前 Host 的同类状态。
- 行由统一状态快照驱动，UI 不承担选路决策。

### Panel 接口与统计

扩展现有房间／成员／会话 API，至少提供：

`room_mode`、`active_path`、`relay_ready`、`direct_ready`、`switch_phase`、`last_reason`、`updated_at`、玩家公网 IP、直连端点、对应 RTT。

Panel 在现有成员／会话表增加展示，并记录路径切换事件。状态缺失或过期明确显示，不能持续冒充实时状态。

- 客户端上报仅用于运行状态展示，不参与权限判定。
- 路径切换保持同一逻辑游戏会话，不制造虚假的退出／进入记录和在线人数变化。
- 服务端流量继续表示实际经过中继的流量；保留备用连接不等于业务正在走中继。
- 不通过中继流量推算 P2P 流量；现有直连计量保持独立口径。

## 5. 执行顺序与验收

### 执行顺序

1. 保存本交接文档，建立 `v5.0.0Full` 开发副本，记录基线校验结果。
2. 实现 AUTO 协议、逻辑游戏流、精确配对和中继附着；先验证纯中继下的完整数据传输。
3. 接入直连承载，实现升级、回退、重放、备用恢复及多人隔离。
4. 接入房间能力校验、生命周期、客户端状态和 Panel。
5. 完成故障注入、手动模式回归、真实网络验收及版本／构建材料更新。

每阶段必须有实际验证结果。不能只完成 UI 或状态机，就声称 AUTO 已完成。

### 必须通过的验收

- **中继先可用：**阻断打洞时仍可正常开始游戏；后台尝试不阻塞中继业务。
- **连接连续：**持续双向传输中完成中继 → 直连 → 中继；两端原本地 TCP 连接保持，字节数量、顺序和哈希一致。
- **真实游戏：**已进入世界后升级、拔掉直连路径后回退，不返回服务器列表、不重新登录。
- **故障覆盖：**单向 UDP 黑洞、仅业务数据不通但保活正常、切换时断路、重复迟到帧、未确认数据非空时回退。
- **背压与结束：**慢接收端、缓存满、并发大流量、FIN/RESET；无静默丢字节、内存无界增长或线程卡死。
- **多人混合：**至少三名玩家分别处于直连、中继、反复回退状态；互不串流、互不影响。
- **多流与后加入：**同一玩家多 TCP 流正确绑定；后来加入者及新流先中继再升级。
- **备用恢复：**只断中继数据连接时，健康直连继续；恢复后仍是原逻辑会话，并能再次回退。
- **生命周期：**停止、踢人、关房、Host 更换、控制失联均遵循管理规则，旧数据不进入新会话。
- **兼容及展示：**旧客户端能力拒绝明确；手动两模式行为回归通过；所有连接方式均显示正确的玩家 IP 来源和实际路径。

受控环境中，RTT 不超过 200 ms、中继健康时，直连黑洞后的**业务恢复目标为 3 秒内**；这属于验收目标，不承诺任意网络下零卡顿。

真实 NAT、多人 Minecraft 实测或构建环境尚未具备时，执行模型必须明确列出待验收项，不能用模拟结果替代实测，也不能把旧版可执行文件标为 v5。

**交付判定：实现代码、协议说明、交接文档、测试记录及版本材料相互一致；所有已确认要求均有对应验收证据。**
