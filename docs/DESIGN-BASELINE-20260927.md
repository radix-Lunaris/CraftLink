# CraftLink —— 设计基准（2026-09-27 用户逐条确认，**以此为准**）

> 来源：用户《设计思路.txt》+ 本轮 8 条 BUG + 用户对 5 个待确认点的答复。
> 任何实现与本文冲突 → **以本文为准**；有疑问先问，不要自己发明。

## A. 身份与房间（§1–§4、§10、§12）

* Owner = 创建房间的账号，**身份永久绑定房间、不可转移**；房间参数（人数上限、连接模式、Host 相关参数）**创建后冻结**。
* 加入房间必须**从 Server 拉取当前房间状态并应用**，本地旧参数不得覆盖（连接模式/人数/Host 状态尤其）。
* 一个房间**最多一个 Host**，可以暂时没有 Host。
* **Owner 离开（主动或被动判定为真正离开）→ 房间立即销毁**：所有人退出/断开、Host 释放、所有连接与 Timer 清理。**不得出现任何人继承 Owner 或房间继续存在**。
* 只有 **Owner** 能切模式；Host（非 Owner）无权。

## B. Host 规则（§4、§12）—— 用户本轮确认

* **无 Host**：任何玩家不能开始 STUN/P2P 连接，提示「当前房间暂无 Host，请等待 Host 认领」。
* **有 Host 但 Host 未开始连接**：其他玩家点开始连接**不得进入正式 P2P 流程**，提示「Host 未连接，请等待 Host 开服」。
* **Host 已连接**：其他 Player 才允许开始连接。
* **Host 掉线**：服务器心跳超时会把它清理掉 —— 那就**按"真正离开房间"处理**（=§12-B：所有 Player 连接立即断开、释放 tunnel、清状态、清 Timer、**释放 Host 位**、重算按钮）。
* **UI 不新增"离线"字样**：沿用现有三种即可 —— 没人认领 / `xxx（未开服）` / `xxx`。
* **Host 恢复后，玩家必须手动重新开始**（不自动替玩家重连）。
* 被踢 / 超时踢掉 = 离开房间。

## C. 被动掉线的统一处理（用户本轮确认，host/player 同规则）

断线重连时先判断：

1. **token 是否仍有效 / 是否已被服务器踢掉**
   → 被踢 / 失效：**按退出房间处理**（不重连、收拾干净、提示）。
2. **没有被踢（真·闪了一小下）** → **自动重建**。

自动重连只允许这两类：**模式热切换** + **被动意外掉线**；其他情况一律手动点开始连接。

## D. 每次打洞前必须重新确认（§5）

* **Player**：每轮开打前**重新拉当前 Host**，确认自己的打洞目标；**只认 Host**（与谁创建房间无关）。不得复用上一轮的 Host ID/endpoint/candidate。
* **Host**：每轮开打前**重新拉当前所有 Player** 生成目标列表（C 走了、E 来了，列表必须更新）。
* **已经打通的连接，在"游戏中新人加入"时不得被影响**；但**换模式这类事件必须严格重建全部通路**（否则通道会不可用）。

## E. 打洞前的严格流程（§7）

```
确认当前 Host → 确认当前目标 → NAT 测量 → 入站策略测量 → 上报测量结果
→ 等待双方都完成（= 等待同步起跑）→ 同步 candidate → 双方确认 candidate
→ 同步起跑 → 同步起降 → Punch → Connected / Failed
```

* **测量是在点「开始连接」之后按这个顺序做的**（不是打开软件就测）。
* **「等待同步起跑」= 先测完的一方等对端也测完测量**（用户确认）。
* 任何一步双方状态不一致 → **不允许继续**，必须等待同步。

## F. 每个 Host↔Player 是完全独立的 Connection Session（§6、§8、§9）

* 独立拥有：session_id / attempt_id / candidate / NAT 状态 / 入站策略 / 同步状态 / punch 状态 / punch 次数 / batch / packet sequence / 当前端口 / punch interval / timer / connected / latency。**不得把一条目标的状态复用到另一条**。
* 双端必须严格同步 attempt_id、batch、序号、尝试次数、端口、阶段；出现「Host 第 10 次 / Player 第 6 次」这类错位 → **作废当前 attempt → 清理 → 重新同步 → 同步起跑 → 同步起降 → 重新 Punch**（这条比"尽快打洞"更重要）。
* **Timer**：每个 Host↔Player 独立一套；**一次连接（不论成功或失败）到达终态 → 该连接的 Timer 立即停止、清零、释放**；下次重连**重新创建**。
  * 用户确认：**一次使用后直接清零，不保留任何"最终耗时"**；重连从 0 重新计算。

## G. UI（§13–§16）—— 只改显示，**不许为修 UI 动 P2P 逻辑**

三层，父级只做汇总：

1. **通路**：`直连尝试中... 0/3` → `P2P 直连中... 2/3` → `P2P 已直连：3/3`
2. **打洞进度**：`正在建立 3 条连接` → `2/3 已完成` / `打洞完成：全部 3 个目标已打通` / `2/3 成功，1 个目标失败`
3. **逐目标明细**（每目标一行，实时阶段）：
   `等待同步起跑（3s）【A】N/C` / `等待同步起降（1s）【A】N/C` / `打洞中【A】第 3 次 · N/C` / `P2P 已直连【A】18ms`
   * 未建立连接前延迟显示 **N/C**；已建立后显示真实 P2P 延迟。
   * 目标来一个加一行、走一个删一行，不留空行。

## H. Host 位的保留 / 清除（用户 2026-09-28 追加确认）

* Host **可以自由主动停止连接再重新开始**（停止 = 未开服），**仅"静默/停止"不清除主机位**。
* 只有两种情况清除主机位：**① Host 离开房间**（主动离开 / 被踢 / 掉线判定为真正离开）；**② Host 主动释放**。
* UI 沿用现有三态：没人认领 / `xxx（未开服）` / `xxx`；未开服时其他玩家点开始连接 → 「Host 未连接，请等待 Host 开服」（`ERROR HOST_NOT_READY`）。

## H-2. 连接状态 ≠ 身份/职位（用户 2026-09-29 强调）

* **连接断开/主动停止**只影响"连接"：玩家连接断开、逐目标行显示"Host 已断开连接/未开服"，但 **Host 位保留**，其他人**不能**因此认领；Host 随时可再开始连接。
* **释放 Host 位只有两条路**：Host **离开房间**（主动/被踢/被服务端真正清退，即房间身份结束）或 Host **主动释放**。
* **token 仍有效的连接抖动 = 没离开房间** → 保留职位 + **自动重连**；token 失效/被清退 = 离开房间 → 释放职位、需重新登录加入。
* 同一原则适用于普通玩家。代码与测试必须把"连接状态"与"房间身份/职位"分成两套状态。
