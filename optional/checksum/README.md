# `optional/checksum/` —— 下载哈希校验留档（**我们不再提供**）

> ## 这不是主交付的一部分
>
> * 官方发布包里**没有**这个目录；
> * 我们**不再提供**「下载页哈希校验」这项附加能力：主交付的服务端不需要它，
>   客户端也不再由我们的官网统一分发；
> * 未来开发者想给用户一个"下载完能核对"的值，可以自行实现 ——
>   这里是**我们原来的实现，供参考**。

## 1. 它当年解决什么问题

官网的下载页上写着三个数字：**版本 / 大小(字节) / SHA-256**。用户下载完可以
自己算一遍哈希，确认文件在传输途中没被改过。问题是：**发新版时人会忘记同步
页面上的数字** —— 页面写着旧哈希，用户一核对就以为文件坏了。

所以有了这个自检脚本：它拿「页面里写的 SHA-256 / 字节数」和「站点里真实 exe
的 SHA-256 / 字节数」逐项对比，**对不上就报错**。它的设计是"故意的"：
exe 一换新，脚本立刻变红，提醒你去改页面上的三个数字。

## 2. 我们的实现

| 文件 | 说明 |
|---|---|
| `check-download.py` | 发布前自检脚本。原路径是早期官网的 `site/scripts/check-site.py`，摘出来时改成可指定站点目录，三个检查项一个没减 |

它检查三件事（任何一项不符 = 退出码 1）：

1. 下载页里存在指向客户端文件的下载链接；
2. 页面上的 `SHA-256: <64 位十六进制>` 与实际文件一致；
3. 页面上的 `大小(字节): <数字>` 与实际文件一致。

用法：

```bash
# 默认校验 ../site/download/CraftLink.exe 与 ../site/download.html
python3 optional/checksum/check-download.py

# 站点在别处 / 文件名不同
python3 optional/checksum/check-download.py \
    --site /path/to/site --page download.html --file download/CraftLink.exe
```

## 3. 只想抄思路的话

三行伪代码就够了，不必用我们的脚本：

```
real_sha, real_size = sha256(文件), 文件字节数
assert 页面里的 SHA-256 == real_sha     # 不一致 -> 让人去改页面
assert 页面里的 大小(字节) == real_size  # 不一致 -> 让人去改页面
```

再往前一步、更省事的做法（推荐给未来开发者）：

* 页面**不要写死哈希**，改成一个由发布脚本生成的 `SHA256SUMS` 文本文件 +
  页面直接链接它 —— 少一处手工同步；
* 或者干脆把哈希写进构建流水线（CI 里生成页面 + 校验，人只审 diff）。

## 4. 注意

* 脚本本身**不需要网络**、不依赖第三方库（纯标准库）；
* 它只对"我们自己发 exe 的官网"有意义；主交付的完整性核对是另一套，仍然随包
  走：服务器上 `sha256sum -c BUILD.txt` 核对"传上去的文件是不是这一份"。
