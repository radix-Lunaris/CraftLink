技术路线 · Relay 模式

一条中继链路，
把局域网世界接到朋友那边。

CraftLink 的技术选择很朴素：不解析游戏协议，不改造游戏，只把字节搬过去。 这一页讲清楚它为什么这样做、数据具体怎么走，以及规划中的 STUN 直连会带来什么变化。

01 · 中继转发原理

房主的局域网上，多了一台「搬运工」

Minecraft 的「对局域网开放」只在本机 127.0.0.1 上开了一个端口，全世界只有这台电脑能连。 CraftLink 客户端把发往这个端口的字节读出来，交给中继服务器，再从中继取回朋友发来的字节写回游戏 —— 游戏全程以为自己在跟本机的一个客户端说话。

一次连接的三个动作

  1. 房主开世界 → 客户端与中继建立主机隧道，登记房间。
  2. 朋友加入 → 客户端与中继建立玩家隧道，中继把两条隧道对接起来。
  3. 对接完成后，两个方向都只是搬运字节，直到有人断开。

为什么这样最省事

  • 游戏版本、模组、整合包都不需要客户端理解 —— 它只搬字节。
  • Minecraft 那边永远是「连本机」，不需要任何额外设置。
  • 游戏协议更新不影响中继，中继本身不需要跟着升级。
02 · 为什么需要中继

因为大多数人没有公网 IP

局域网世界要给别人连，常规做法是端口映射或内网穿透。它们不是不能用，而是对普通玩家要求太高、 对网络环境太挑。中继把「让两边能互相看见」这件事，从玩家家里搬到了一台固定在线的服务器上。

端口映射：要动的环节太多

  • 需要运营商给到公网 IP —— 很多家庭宽带和校园网已经没有了。
  • 需要进路由器后台改 NAT / 防火墙规则，普通玩家容易改坏。
  • 需要把游戏端口直接暴露在公网上，谁都能扫到。
  • IP 一变、路由器一换，规则就得重配。

中继：玩家这边零配置

  • 房主和朋友都不需要公网 IP，也不需要路由器权限。
  • 只有中继服务器需要一个公网地址，而它只需要一个出口。
  • 房主的游戏端口始终留在本机，不对公网暴露。
  • 跨校园网、跨运营商、跨地区都能用同一套流程。
代价要说清楚

走中继意味着数据多绕一跳，路径是「房主 → 中继 → 朋友」。所以体验取决于三方到中继的网络质量： 同城、同省的朋友体验接近直连；跨运营商、跨地区会明显一些。中继本身只转发字节， 它不做加速，也不会让原本很差的线路变好。

03 · 房间与主机位置模型

房间名是钥匙，主机位置是座位

这是 CraftLink 里最容易搞混、也最值得讲清楚的一对概念： 房间是大家一起待的地方，主机位置（host）是房间里唯一一个「连着 Minecraft 世界」的座位。

房间（Room）

  • 用房间名标识：中文、英文、空格都可以，同名就是同一个房间。
  • 程序内部会自动生成一个房间 ID 来做实际标识，玩家不需要看到它。
  • 房间的寿命绑定在成员的连接上：人都走了，房间自然就空了。

主机位置（Host）

  • 房间里唯一的位置，先到先得：谁先开世界谁持有。
  • Minecraft 的连接绑定在这个位置上，只有它能连到房主的游戏。
  • 在客户端点「停止开服」只释放世界，不释放位置；想换人开世界，必须点「释放主机身份」。
  • 持有者断线或关闭客户端时，位置会被回收，别人可以接手。

04 · 数据通路

中继不解析 Minecraft 协议

从中继的视角看，房间里流动的就是一串字节。它不知道什么是登录包、什么是区块数据， 也永远不会去改一个字节 —— 这条通路是原始 TCP，双向透明。

中继看得见什么、看不见什么
层面 中继服务器
能看到 房间名、房间 ID、成员连接、主机位置状态、每条隧道的字节流量与在线情况。
不能看到 Minecraft 的包类型、玩家聊天、世界数据含义 —— 它不解析协议，拿到什么就转什么。
会不会改数据 不会。不重组、不拆包、不压缩、不重排，按收到的顺序原样转发。
控制信息怎么走 加入房间、主机状态这类控制信息走的是一条独立的控制连接，不会混进游戏数据里。
这条通路是冻结的

「只转发字节」不只是实现细节，而是这个项目刻意守住的边界： 它让中继对 Minecraft 版本、模组、整合包完全免疫，也让排错变得简单 —— 游戏连不上时，问题要么在客户端到中继这一段，要么在游戏本身，不会藏在中间那台服务器里。

05 · 客户端与服务端分工

谁负责什么，一眼看清

两边的职责几乎没有重叠：客户端负责「和游戏打交道」，服务端负责「让两边见上面」。

CraftLink 客户端（Windows 单文件）

  • 读取本机 Minecraft 局域网的字节，并写回游戏。
  • 和玩家那边的本地端口对接，让 Minecraft「连本机」。
  • 房间的创建与加入、主机身份的申请与释放。
  • 界面、语言（中 / 英 / 日）、主题（暗 / 亮 / 跟随系统）。
  • 连接状态与日志，方便自己排查问题。

中继服务端

  • 维护房间表与房间内的主机位置（先到先得）。
  • 按房间名把两边配对，建立一人一条的隧道。
  • 对接完成后只做字节转发，不做任何协议处理。
  • 成员离开、连接断开时回收位置与隧道。
06 · 规划中

STUN 直连与 AUTO 调度：敬请期待

中继路线会一直保留 —— 它是「一定能连上」的那条路。在这之上，我们计划再加一条更近的路。

STUN 直连 敬请期待

借助 STUN 探测双方的可达地址，让数据在两边之间直连，不再绕经中继。 同城、同省的朋友有机会拿到更短的路径。

  • 仅 STUN，不涉及任何需要改路由器的操作
  • 打洞失败必须能自动回落到中继，不允许出现「以前能连、现在连不上」

AUTO 调度 敬请期待

由客户端自动判断该走直连还是中继，玩家只需要点一次「开始连接」。 现在这个开关是锁着的：没有把握稳定之前，不会放出来给玩家踩坑。

  • 不做假实现、不写「即将上线」的具体日期
  • 路线确定后会在下载页与更新摘要里说明
关于实测数据

我们不在这里写「延迟多少毫秒」「能带多少人」这类数字。网络质量取决于三方之间的实际线路， 写一个固定数字只会误导人。定性地说：同城、同省的朋友体验接近直连； 跨运营商、跨地区会有明显绕路感。真实的对比数据会在有稳定测试环境后再公开。
